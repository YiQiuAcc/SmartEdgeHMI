# 数据保留策略

> 引入版本：v1.2.x（TASK-104，2026-11-17）｜ 代码：`SmartEdgeHMI/Data/Retention/`
> 相关：[performance-benchmarks.md](performance-benchmarks.md) · [next-steps-v1.2.md](next-steps-v1.2.md)

## 1. 为什么需要它

遥测表按 1 Hz 采样，单设备一天 86,400 行、一年约 3,150 万行；报警表则只增不减。本项目此前**没有任何删除逻辑**——全仓唯一的 `DELETE FROM` 在基准工程里。边缘设备磁盘有限，长期运行必然写满，写满后 SQLite 写入失败、WAL 无法 checkpoint，最终表现为"采集还在跑，但历史查询全空"。

保留策略要解决的是：**让数据库大小有上界，同时不丢审计需要的记录。**

## 2. 配置（`appsettings.json` → `DatabaseSettings`）

| 配置项 | 默认值 | 语义 |
| --- | --- | --- |
| `RetentionDays` | `30` | 遥测保留天数；`<= 0` 关闭遥测清理 |
| `AlarmRetentionDays` | `0` | 报警保留天数；`<= 0` 关闭报警清理（默认关闭） |
| `RetentionCheckIntervalHours` | `24` | 后台清理周期（小时） |

设计取舍：

- **报警默认不清理**。报警是 ISA-18.2 语境下的审计记录，删了就无法追溯"当时为什么报警、谁确认的"。需要归档时由运维显式配置 `AlarmRetentionDays`，或先导出再清理。
- **配置非法不启动清理**。三个值都用 `int.TryParse` 防御式解析，缺失/非法回退默认值；不会因为写错配置就把库清空。

## 3. 行为

1. 主程序启动、数据库初始化完成后调用 `IDataRetentionService.Start()`，**立即执行一轮**，之后每 `RetentionCheckIntervalHours` 小时重复。
2. 每轮按 `utcNow - RetentionDays` 计算截止时间，**严格小于**截止时间的行才删除（等于截止时间的保留，便于按天对齐核对）。
3. 删除按批进行：每批 `5000` 行，批间 `Task.Delay(50ms)`，单轮最多 `200` 批（100 万行）。达到上限时本轮停止并记 `BatchLimitReached=true`，剩余积压留给下一轮——避免一次清理长时间占用连接、把实时写入饿死。
4. 两张表互相隔离：遥测清理失败不影响报警清理，反之亦然；异常只记日志，下一轮重试。
5. 删除 0 行时不写日志（避免每 24 小时产生噪音）；有删除时记一条摘要（含保留天数、删除行数、是否触顶）。
6. 退出时 `DisposeAsync` 取消后台循环并最多等待 5 秒。

## 4. 已知边界（诚实口径）

- **库文件不会自动变小**。SQLite 删除行只把页标为空闲，文件大小不变。回收磁盘需要 `VACUUM`（会重写整库、需要额外磁盘空间，不适合在采集运行中直接跑）。本策略的目标是"文件不再增长"，不是"文件变小"。若确实需要收缩，建议停机维护窗口执行 `VACUUM`。
- **单轮上限 100 万行**。若设备离线很久后重新上线、积压远超上限，需要多轮（多天）才能清完；日志里的 `BatchLimitReached` 是可观测信号。
- **未验证 24 小时以上的长期收敛**。单元测试覆盖了保留边界、1.2 万行分批、关闭语义、幂等与清理后新数据可查；"连续运行一天后库大小是否稳定"需要在真实设备上观察，属后续验证项。**已做一次 25 分钟有界观察**（2026-11-17，JSON 模拟器 1 Hz）：遥测 24 分钟内 65 → 1506 行（≈60 行/分，符合 1 Hz），库文件按页增长 4,096 → 262,144 字节，`-wal` 从 1.22 MB 涨到 **4.13 MB 后稳定不动**（checkpoint 自限），进程工作集 182–189 MB、私有内存 104–108 MB 全程平稳；按 1 Hz 线性外推 30 天约 260 万行、库文件数百 MB 量级。24 小时以上仍未验证。
- **WAL 文件**。清理发生在 WAL 模式下，checkpoint 由 SQLite 自行调度；上述 25 分钟观察中 `-wal` 稳定在约 4.13 MB（约 1000 页），未观察到无界增长。

## 5. 运维动作

| 场景 | 做法 |
| --- | --- |
| 调整保留天数 | 改 `appsettings.json` 的 `DatabaseSettings:RetentionDays` 后重启（配置在启动时读取一次） |
| 临时关闭清理 | `RetentionDays: 0` |
| 清理报警 | 先备份库文件，再设 `AlarmRetentionDays`（如 `365`） |
| 确认清理是否生效 | 搜日志 `数据保留清理完成`，或在库里 `SELECT MIN(Timestamp) FROM TelemetryHistory` 看最早时间是否前移到保留窗口内 |
| 回收磁盘 | 停程序 → `VACUUM` → 重启 |
