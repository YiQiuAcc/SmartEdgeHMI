### 1.1 执行环境的两处修正

- **计划端口 COM3 不可用**：`Get-PnpDevice -Class Ports` 显示 `USB-SERIAL CH340 (COM3)` 为 `Unknown`（上次插在其它 USB 口留下的幽灵条目），`COM4` 为 `OK`。按真实枚举改用 COM4。

## 3. HW-02 拔插重连

### 3.1 不干预（第一轮，4 次断链全部自愈）

| 断链 | 轮询恢复 | 耗时 |
| --- | --- | --- |
| 14:28:52.452 | 14:29:02.455 | 10.0 s |
| 14:29:07.508 | 14:29:17.511 | 10.0 s |
| 14:29:24.889 | 14:29:34.891 | 10.0 s |
| 14:30:04.996 | 14:30:15.000 | 10.0 s |

每次均为「5 s 重试第 1 次成功 + 5 s 稳定期」，随后恢复轮询并**自动重下发配置阈值**。
拔出瞬间：`[ERR] [SerialPort] COM4 ReadLoop 未预期异常退出` → `第 1/5 次重连, 等待 5000ms` → `[ERR] 串口 COM4 链路故障`，明确报错、计数可见。

注：4 次中 2 次为用户主动拔插，另 2 次未由观察器判定为端口移除（推测接触抖动瞬断），额外覆盖了连续抖动场景。

### 3.2 干预（第一轮，暴露 F-3）

| 时刻 | 事件 |
| --- | --- |
| 14:22:43.773 | 手动点「连接」→ `[SerialPort] 已打开串口 COM4` |
| 14:22:43.773 | 同一毫秒：`第 4/5 次重连, 等待 40000ms` |
| 14:22:43.774 | `重连已达最大次数 5, 放弃重连` |
| 14:22:43.776 | `[ERR] 串口 COM4 链路故障` |
| 14:23:29 起 | 遥测永久停止增长 |

端口打开成功后被旧任务拆除，轮询未启动。14:23:51.211 复现同样序列。

### 3.3 第二轮（`275a6d6`）

- **含竞态回归**：刻意在 5 秒重试窗口内点「连接」→ 打开成功后**无**「放弃重连」/「链路故障」，轮询 5 s 后恢复，数据连续。
- **不干预**：15:16:48.842 断链 → 第 1/5 次（5 s）打开失败（设备尚未枚举完）→ 第 2/5 次（10 s）成功 → 15:17:08.846 轮询恢复，耗时 **20.0 s**。
- 备注：恢复耗时实测区间 **10–20 s**。固定退避（5/10/20/40 s）不考虑 USB 枚举耗时，若第一次 5 s 重试落在枚举完成之前就要等下一次 10 s。模板中「上电后 10s 内恢复出数」的预期偏乐观。

## 4. HW-03 异常报文

**替代说明**：注入需要独占上位机 RX 链路，而应用已独占 COM4。故在 ELTIMA 虚拟串口对执行（应用占 COM1 / 注入器占 COM2）。被测对象是上位机**解析器**，与传输介质无关。

基线 664 行 → 注入后 684 行，每例 10 次：

| 用例 | 结果 |
| --- | --- |
| 坏 CRC（内容带哨兵 50.0°C / 60.0%） | **入库 0 行**，静默丢弃 |
| 截断半帧（4 字节） | 无脏数据入库 |
| 粘包（两帧无间隔连发，值 31.0°C / 62.0%） | 恰好 20 行（每对时间戳成对），**无错位** |
| 超长帧（100 B，头部伪装 FC03） | 无脏数据、无越界 |

注入窗口日志无任何 ERR，进程 `Responding=True` 未崩溃。
代码佐证：`ModbusProtocolParser.TryProcessNextFrame` 对每帧做 CRC 校验，不匹配则 `reader.Advance(1)` 继续搜寻帧头；按功能码 + ByteCount 计算期望帧长切帧。

## 5. HW-04 / HW-05 / HW-06 与缺陷

### 5.1 HW-04 指令下发 — 通过（带备注）

| 步骤 | 下发 | 设备响应 | 上位机观测 |
| --- | --- | --- | --- |
| 阈值 | UI 滑块 60→25 °C → `下发阈值至 COM4: 25°C (地址 0x0002 ← 写入值 250)` | 状态 1→4，错误码 0→302 | 入库 `StatusCode=4, ErrorCode=302`；产生 `ThresholdExceeded` 报警（触发值 29.7） |
| 恢复 | UI 滑块 25→60 °C | 状态回 1 | `[ISA-18.2] 恢复 UNACK→RTN_UNACK`；`AlarmHistory.State=2`、`ClearedAt=14:17:09.516` |
| 复位 | UI「设备紧急复位」→ `复位指令已发送至 COM4` | 29.5→25.1 °C，湿度 44.9→46.4% | 入库数值跟随 |
| LED | 探针 `FC06 addr 4 = 1 / 0` | 寄存器读回 1 / 0 | **人工目视确认：亮 / 灭** |

- 步骤 3 边界：上位机**没有** LED 控制入口，只能由探针直接发帧（缺陷 F-6）。
- 阈值方法学：模板要求「FC03 回读地址 2 验证阈值」不可执行——地址 2 读回是状态位（缺陷 F-4）。改用行为验证。

### 5.2 HW-05 断电恢复 — 通过（带备注）

- 用户拔 USB 断电 8 s 后插回；应用与看门狗提前关闭，插回后由探针直接读，无人覆盖状态。
- 断电前 26.7 °C / 45.7% → 冷启动后 **25.1–25.4 °C / 43.1–43.3%**，状态 1、错误码 0、LED 0。
- **确定性证据**：受控 DTR/RTS 硬复位捕获 **278 字节启动乱码**（ESP8266 boot ROM 的 74880 波特输出在 115200 下的错位帧），复位后立即 6/6 有效响应，首帧 **25.0 °C / 45.4%**，随后 4 秒内即漂移到 24.6 °C / 46.1% —— 证明上电默认 25.0 °C / 45.0% 且从首样本起自然漂移。
- 诚实边界：单看物理断电后的寄存器读数，「冷启动回默认」与「连续运行漂移」不能完全区分（湿度偏差在随机游走 1σ 内），故不单独宣称，以上电硬复位证据为准。
- 阈值上电默认 80.0 °C **不可验证**（F-4）。

### 5.3 HW-06 Watchdog 重启 — 第一轮失败，第二轮通过

**第一轮（`c9997a5`）失败**

- `taskkill /F` 强杀 pid=13024（14:19:03.441）→ 看门狗拉起 pid=22756（14:19:04.479，**1.2 s**），远低于 10 s 预期。
- 看门狗日志完整：管道断开 → `HMI 主进程已退出 (ExitCode: 1), 正在重启...` → `HMI 主进程已启动` → `已连接到 Watchdog 命名管道` → 心跳恢复。
- 端口无残留占用（探针可独占打开 COM4）。
- **但重启后不恢复数据**：协议回落 **JSON**、无自动连接（日志无 `[SerialPort] 已打开串口`，UI「未连接」），需人工「选 Modbus + 点连接」才恢复。
- 判定：**失败**。看门狗只保证进程存活，不保证系统可用。

**第二轮（`275a6d6`）通过**

| 时刻 | 事件 |
| --- | --- |
| 15:14:53.951 | `taskkill /F` 强杀 pid=21344 |
| 15:14:55.816 | 看门狗拉起新进程 pid=4720（**1.9 s**） |
| 15:14:56.759 | `[AutoConnect] 自动连接上次使用的串口 COM4` |
| 15:14:56.767 | `[SerialPort] 已打开串口 COM4` |
| 15:15:01.772 | `[Modbus] 已启动 COM4 的轮询任务` |
| 15:15:01.779 | `[Modbus] 下发阈值至 COM4: 60°C` |

**从强杀到 Modbus 轮询恢复 7.8 秒，全程零人工操作，协议保持 Modbus。**

### 5.4 第一轮暴露的缺陷（均已修复）

| 编号 | 级别 | 标题 | 状态 |
| --- | --- | --- | --- |
| F-1 | P1 | 通信协议选择不持久化，重启回落 JSON | 已修复（`275a6d6`） |
| F-2 | P1 | 重启后不自动连接串口 | 已修复（`275a6d6`） |
| F-3 | P1 | 手动重连与在途重试竞态，旧任务拆除新连接 | 已修复（`275a6d6`） |
| F-4 | P2 | 阈值只写不可回读（FC06 addr2 写阈值 / FC03 addr2 读状态） | **未修复**，模板已标注规避口径 |
| F-6 | P3 | 上位机无 LED 控制指令（FC06 addr4） | **未修复**，验收用探针 |

F-3 根因（`SmartEdgeHMI/Protocols/Transports/Serial/SerialPortService.cs`）：

1. `RunReadLoopWithReconnectAsync` 的循环只判断 `_disposed` 与 `attempt`，不判断取消信号。上下文被手动重连取消后，`HandleReconnectDelayAndOpenAsync` 内的 `Task.Delay(delay, ctx.Token)` 立即抛出 `OperationCanceledException` 并返回 false，循环 `attempt++` 继续，**毫秒级烧完剩余次数**。
2. `FinalizePortState` 到次数上限后**无条件** `_activePorts.TryRemove(portName)` + `CleanupContext(...)`；而该 key 下此时已是**新连接**的上下文 → 刚打开的新端口被关闭并 Dispose。

## 6. 环境行为记录（非缺陷）

- `tools/package.ps1` 重建时会先删除 `dist/publish/<版本>/`，**该目录下的运行时数据库 `SmartEdgeHMI.db` 一并被清空**（本轮观测到遥测从 2750 行归零）。发布目录本就是构建产物，但若直接在生产发布目录上覆盖升级会丢数据，已记入升级边界。
- `pio device list` 与 `Get-PnpDevice` 都不认 `pio run` 之外的 COM3 幽灵条目；判断端口是否存在应以 `HKLM\HARDWARE\DEVICEMAP\SERIALCOMM` 或 `pio device list` 的实际枚举为准。
- pyserial 打开端口会置位 DTR/RTS，使 ESP8266 复位（读到 boot 乱码）。上位机侧 `DtrEnable/RtsEnable` 均为 false，不会触发此复位。

## 7. HW-01 连续运行 ≥ 2h — 通过

**第一轮（作废）**：14:37:06 起跑 35 分钟（2750 行、58–62 行/分钟、日志零新增错误），因修复补丁需重打发布包而中止；`tools/package.ps1` 重建时清理 `dist/publish/1.2.0`，该库同步作废，**不作为 HW-01 证据**。

**第二轮（`275a6d6`，最终证据）**

- 起跑 15:19:44，监控窗口 15:20:01 – 17:25:00，共 **125 分钟 / 125 个采样点**。
- 遥测行数 194 → **7,695**。
- **每分钟新增行数：最少 58、最多 62、平均 60.0 —— 2 小时内无任何一处采样中断。**
- 设备读数区间：温度 **10.3 – 28.3 °C**、湿度 **20.0 – 94.2%**，均落在固件钳位区间（10–60 °C / 20–95%）内，包含触底钳位（湿度精确打到 20.0）。
- 状态码全程恒为 **1**，无误报警、无错误码 302。
- **日志全程 364 行不变、ERR 计数 20→20、WRN 9→9 —— 2 小时内零条新日志，即零错误、零警告、零重连。**

对照第一轮暴露的问题：不自动重连与重连竞态在这 2 小时里一次都没出现。
